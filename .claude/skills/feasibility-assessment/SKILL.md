# Feasibility Assessment

Produce the **Integration Feasibility Assessment** — the first client-facing deliverable of the integration track (`docs/spec-workflow.md` §2.0), from the canonical template `templates/feasibility-assessment.md`, rendered to the FDE-branded docx with `scripts/render_fde_docx.py` (`docs/documentation-standards.md` §1, §1.1). The same template exists as a ready-to-use Word document, `templates/docx/2026MMDD_FDE-Feasibility-Assessment-IntegrationName_ClientName_Factorial.docx`, for anyone working without this harness; when the Markdown template changes, re-render that file in the same change so the two never diverge. Its job is to answer one question for the requester, the client and the FDE lead: **can this be integrated, how, under which conditions, and what is still unknown** — before a Solution Design or a SOW exists.

Output file: `YYYYMMDD_FDE-Feasibility-Assessment-<IntegrationName>_<ClientName>_Factorial.docx` (plus the Markdown source beside it, which is what gets edited and re-rendered).

## Workflow

1. **Intake (AskUserQuestion, one call).** Client name, external system and vendor, who requested and when (ticket / email / specification), target date and what it is tied to, the Factorial modules the client **has hired** and the ones **in the proposal** (never inferred — the requester states them), the documents received (client specification, vendor API manuals, sandbox credentials), and whether an ES twin is required. Ask for anything missing before reading; do not start from assumptions.
2. **Read the request and the vendor material completely.** Extract every fact into two lists — *established* (with the citation: document, section, date) and *not established* (missing by oversight vs supplied per project). Quote, do not interpret. Where the client specification states something about Factorial or about the direction of control that is wrong, record it for section 2.5.
3. **Verify every Factorial capability against the pinned OAS** with the `factorial-oas` skill (`factorial-oas-YYYY-MM-DD.json`, newest snapshot): resources, filters, required fields, lifecycle operations, webhook subscription endpoint. Note the characteristics that shape the design (date-granularity filters, last-change-only timestamps, no external reference field, approval calls, module-specific resources). Anything not in the OAS is an open question, not a fact; production-verified behaviour from another integration (e.g. Wellhub webhook types) is cited as such.
4. **Map capabilities to Factorial modules.** For every requested capability find the API namespace it needs (`templates/data/factorial-product-api-mapping.csv`, reproduced in Appendix B) and compare with the modules the requester listed: a namespace outside the hired modules is a **commercial gap** (section 6, Side = Commercial) with a course of action, never a silent assumption that the client will buy it.
5. **Design ≥ 2 integration approaches** with `peer-architect` (strongest model). Options must differ on something real — Factorial modules required, communication method with the other system (REST / SOAP / GraphQL / database connection / webhooks / file exchange / vendor-built actions), where the logic runs, phasing — and each one states what it accomplishes of the request and what it leaves open. Include the option you will not recommend. Check platform assumptions against `platform-guide.md`; mark unverified ones *to be confirmed*.
6. **Fill the template** (`templates/feasibility-assessment.md` → copy to the client folder as `<date>_FDE-Feasibility-Assessment-<Integration>_<Client>_Factorial.md`): every section present, every `{{placeholder}}` replaced, every grey-italic guidance line and the "How to use" box deleted. Verdict vocabulary is fixed (*Feasible · Feasible with conditions · Not feasible · Unknown — evidence missing*); severity is the consequence if unaddressed (*Critical / High / Medium / Low*); every gap has a side, a course of action and a Blocking flag; every open question names the party that can answer it and what it unblocks. If no verdict can be given yet, section 8 says exactly which evidence or decision is missing and who provides it — it never guesses.
7. **Render and look at it.** `python3 scripts/render_fde_docx.py <file>.md <file>.docx`, then convert to PDF and read the pages (tables that wrap badly get a `<!-- widths: … -->` directive; see `docs/branding.md` §4). Refresh the TOC in Word (F9) before sending. Platform choice is part of the verdict, not a preset: the cover's *Orchestration* and the §2.4 row are filled from the options in §7 (`platform-guide.md` §4), Factorial Code being the default when nothing argues otherwise.
8. **Validate before handing over** (all must hold): no `{{`/`}}` left; no guidance lines; the 10 numbered sections and Appendices A–B present in order; every Factorial statement in §4 and Appendix A traceable to the OAS or to a cited production fact; every row of §6 has Side / Severity / Course of action / Blocking; §1.1 verdicts equal the per-use-case verdicts in §5 and the gaps in §6 are referenced by at least one option in §7; §10 questions cover every *to be confirmed* and every blocking gap; no hedging (`probably`, `I assume`, `should work`); no secrets, tokens or PII.
9. **Report:** the verdict, the blocking items with owners, the open questions grouped by party, and what the field-mapping workbook needs next (the `design-docs` skill produces it once answers arrive). Offer the ES twin if the project requires one (`documentation-standards.md` §5: translate the final Markdown, render it to `YYYYMMDD_FDE-Evaluacion-de-Viabilidad-de-Integracion-…_Factorial.docx`; never a fork).

## Guardrails

- Never state a Factorial endpoint, field, filter or module boundary from memory — cite the OAS file and path, or write the question.
- Never present a vendor capability as available when the documentation only describes transport; "the manual does not say" is a finding.
- Never let a schedule promise rest on an unowned prerequisite — Phase 0 items need an owner and a date.
- Never pick the collision rule, identity key or module purchase on the client's behalf; lay out the options and put the decision in §10.
- Never widen the scope: dependencies outside both systems are referenced, not assessed.
- Never edit the rendered docx by hand — change the Markdown and re-render, so the twin and later revisions stay mechanical.
